- Debugging an undersized malloc in StationNew

In my first draft, I wrote:
Station new = malloc(sizeof(Station));

and later:
Station new = malloc(sizeof(Station *));

Given that in station.h defines:
""typedef struct station * Station;""

Station is already a pointer type, so sizeof(Station) = size of one pointer(8 bytes);
And Station * is a pointer-to-a-pointer, which is also just 8 bytes.
so the correct version should be Station new = malloc(sizeof(struct station));

what is tricky about this is that it does not show up immediately, instead, when running the testing, 
bugs occured at somewhere unexpected. acter carefully checking, nothing wrong about that function
but the since the report showed that there is something wrong about the memory allocation, 
I went back and check the real problem. After some research, I figured out that if I only 
asked for 8 bytes of memory but writing beyond that, program is not going to crash immediately 
beacuse what I did is just quietly overwrite bytes that belongs to something else or bytes that
happen to be unused. but, for example, free() is called, the allocator's internal bookkeeping is 
broken. So I end up debugging a crash in a function that has nothing to do with the actual bug,
with no obvious link back to StationNew.

- double free crash in realloc

first version i had:
int *rooms;
...
rooms = realloc(rooms, sizeof(int));

this crashed with asan saying double free inside realloc, but i never called free anywhere near
that code, so at first i had no idea what was even going wrong. turned out rooms was uninitialised
so it held garbage, and realloc treats any non-NULL pointer as if it came from malloc/realloc
before. my garbage value happened to match an address that had already been freed somewhere else
in the program (in stationReader.c), so realloc thought it was being asked to free something that
was already gone. fixed it by mallocing the array once up front, sized to the number of rooms in
the station, instead of growing it one int at a time with realloc.

for (int count = 0; count < nV; count ++) {

loop early if u is still -1 after the scan, since there's nothing left worth relaxing.

- went back through Station.c and evacuation.c one more time before submitting, checking
correctness properly instead of just relying on the provided tests passing. found two real bugs
that all four tasks had already "passed" with.

- dijkstra was overwriting dist[i] with no check that the new path was actually shorter

for (int i = 0; i < nV; i ++) {
    int add_dist = StationContainsCorridor(s, u, i);
    if (add_dist != NO_CORRIDOR && !included[i]) {
        dist[i] = dist[u] + add_dist;
        pred[i] = u;
    }
}

this is the one thing dijkstra is actually supposed to guarantee - only update a room's distance
if the new path through u is shorter than what's already there. as written it just overwrites
dist[i] any time there's an edge to it, even if the existing value was already better. e.g. if
room A connects to both B (weight 1) and C (weight 1), and B also connects to C (weight 100), the
correct dist[C] is 1, but after processing B this code overwrites dist[C] to 1 + 100 = 101,
destroying the correct value. none of the provided tests happened to have a graph shaped like
this, so it passed everything anyway, which is exactly why it's worth catching now rather than
assuming "all tests pass" means the algorithm is actually correct. fixed by only updating when
the new distance is smaller:

int new_dist = dist[u] + add_dist;
if (new_dist < dist[i]) {
    dist[i] = new_dist;
    pred[i] = u;
}

- check_block only ever checked the first blocked corridor

static bool check_block(struct blockedCorridor blocked[], int room1, int room2) {
	if (room1 == blocked->roomA && room2 == blocked->roomB) {

blocked->roomA is the same as blocked[0].roomA, so this never looked at numBlocked at all - it
only ever checked whether the corridor matched the very first blocked corridor in the array.
works fine for the sample tests since they only ever block one corridor at a time, but with two
or more blocked corridors it would silently ignore all but the first one. fixed by looping over
numBlocked and checking every entry:

static bool check_block(struct blockedCorridor blocked[], int numBlocked,
		int room1, int room2) {
	for (int i = 0; i < numBlocked; i ++) {
		if ((room1 == blocked[i].roomA && room2 == blocked[i].roomB) ||
		    (room1 == blocked[i].roomB && room2 == blocked[i].roomA)) {
			return true;
		}
	}
	return false;
}

both of these are a good reminder that passing the given tests isn't the same as being correct -
neither bug showed up until i actually read back through the logic asking "what graph would break
this" instead of just running the same test files again.
